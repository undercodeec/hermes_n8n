# OpenAI egress: review prototype, not deployment-ready

**Security review: NO-GO on the shared VPS.** The earlier Docker service and
socket drop-ins have been removed; Docker no longer depends on the guard. This
does not resolve the remaining blockers: the guard cannot prevent a brief
unfiltered window if another actor removes its nftables table, and the current
bridge rules do not establish exclusive OpenAI access. Do not run this prototype
on the shared host until its network, lifecycle and rollback behavior has been
validated in an isolated equivalent environment.

This is a **prototype**, not a production deployment. The included lifecycle design is intended to fail closed under the stated host assumptions, but has not been validated against a real Linux Docker/nftables/systemd installation. Do not deploy until the lifecycle and network tests below pass on the exact host and configuration. There is no automatic table deletion or publishing procedure.

## Design

`firewall.py` runs on the Linux host. In one nftables transaction it creates an initially empty IPv4 destination set and early input, output and forward chains for a dedicated, explicitly named Docker bridge. It then resolves only `api.openai.com`, rejects empty, oversized and non-global IPv4 results, and atomically replaces the set with 45-second kernel-expiring entries. It refreshes every 15 seconds. DNS, nft or file errors do not remove the guard; entries expire. IPv6 and all other routed traffic involving the bridge are dropped. Return packets must match an unexpired address, TCP source port 443 and established conntrack state. `return` does not override Docker's own policy. Host-to-bridge and bridge-to-host traffic is dropped. Local bridge switching is not necessarily processed by these inet chains.

After a successful nft update, the manager atomically publishes a read-only JSON lease; its monotonic expiry is at most 40 seconds from before the update. `proxy.py` accepts only HTTP CONNECT to `api.openai.com:443`, uses only addresses in a current lease, and forwards bytes without terminating TLS. Clients must perform normal certificate and hostname validation. It listens on port 3128 inside its container and requires HTTP Basic proxy authentication from a protected credential file. It bounds concurrent handlers, applies a 10-second absolute header deadline and closes streams idle for 300 seconds. Active streams are not closed merely for exceeding 30 seconds. A lease may disappear or become stale without opening the firewall. Existing connections stop passing packets when their kernel address entries expire. Moreover, a successful refresh replaces the entire set: **a DNS rotation can immediately interrupt existing connections** to removed addresses. Clients need bounded retries where safe; retaining a removed address or an established-flow exemption indefinitely would weaken the fail-closed policy. This availability limitation remains a production blocker until addressed and tested against the actual application. The fixed lease is an upper bound on access after a successful refresh, **not** the authoritative DNS TTL: the system resolver does not expose TTL here.

DNS and SNI do **not** authenticate an IP address or guarantee exclusivity: DNS may be poisoned, IPs may be shared and SNI may be arbitrary or encrypted. The proxy does not inspect SNI and cannot prevent a malicious client from sending other TLS traffic to an allowed shared IP. TLS server certificate/hostname verification is the client's responsibility. This is an IP/port egress restriction, not a cryptographic OpenAI-only destination guarantee. If that guarantee is required, use a separately reviewed TLS-aware enforcement design.

## Lifecycle design for review

The example units under `systemd/` assume files at `/opt/openai-egress`, a root-owned `/etc/openai-egress/image.conf` containing `OPENAI_PROXY_IMAGE` as an independently verified image reference with a SHA-256 digest, and a dedicated Docker bridge network `openai-egress` configured with bridge name `br-openai`. The container is created without published ports, extra networks or a Docker restart policy. The base image digest used to build it must also be independently verified; the image reference check does not establish image provenance. This is not an installation instruction: the guard, supervisor, network and host dependencies must be reviewed together before any activation.

There are **no Docker service/socket drop-ins or dependencies on this guard**, and neither example unit is enabled at boot. Docker and unrelated services must remain independent. Before installing bridge-wide rules, bootstrap requires Docker to report the named dedicated bridge network as empty; an absent, occupied or uncertain network fails without installing rules. Reserve that bridge exclusively: this check cannot rule out all non-Docker uses or races. Bootstrap then creates an empty table, records its nft JSON structure in root-owned `/run/openai-egress/guard.json`, and fails if the table already exists or its structure is unexpected. It never deletes a pre-existing table. The proxy supervisor alone requires Docker and the guard. It verifies the structural snapshot and network, stops and removes only its labelled container, creates a fresh stopped container with `--restart=no`, verifies the guard, refreshes the expiring set and lease, verifies the guard again and only then starts it. It periodically checks the guard and container and refreshes; failures stop the container where Docker is reachable, and systemd retries the supervisor on failure. An abrupt supervisor death leaves the kernel set to expire; on restart it first stops the old labelled container. A proxy that exits is detected at the next check and the supervisor restarts via systemd.

The supervisor is bound to Docker: stopping/restarting Docker stops the supervisor, but **does not automatically restart it** when Docker returns. If Docker is unavailable, stopping the container can fail; with Docker live restore, the container may remain running, although the intact guard's entries expire. A host reboot clears the guard; `--restart=no` is required to keep this proxy stopped, but that assumption and every other activation path must be verified on the target host. Consequently automatic proxy startup after Docker restart, host reboot or firewall reload is deliberately not provided. Controlled recovery must establish that the dedicated proxy and any other workloads on its bridge are stopped, automatic restart is disabled, Docker reports the bridge empty, and the old guard state has been safely handled before starting the guard and supervisor. If any of those facts or their ordering cannot be established, leave the proxy stopped: this is a production blocker.

The supervisor must be the only actor that starts or reconfigures the dedicated container. The label is not an authorization mechanism. No external actor may alter, flush, reload or replace the guard table, its set or the runtime snapshot while the container runs; no privileged container or Docker API user may bypass these restrictions. Structure checks ignore changing set elements and run periodically, not continuously. In particular, external deletion of the firewall can create an unfiltered window before detection, and Docker might be unavailable when the supervisor tries to stop the container. **This implementation cannot guarantee fail-closed operation against such changes.** A host where those assumptions cannot be enforced is a production blocker, not a supported fallback. `firewall.py`'s standalone CLI is not coordinated with these units and must not be used to start this design.

If bootstrap fails after table creation, the table remains in place and a retry deliberately fails rather than replacing it. A guard-unit restart with an existing table likewise fails; first stop every affected container and verify it cannot restart, then an authorized operator may remove the old table and retry bootstrap. Do not stop Docker or unrelated services as a routine recovery action. Never reset or delete the table while a container could transmit. The unit ordering and behavior with Docker live restore, manual Docker invocation, socket activation and other firewall managers must be tested on the actual host; unverified paths block production.

## Mandatory integration and security gates

* Prove that the dedicated bridge name matches Docker's actual interface, and that the Docker host uses nftables with conntrack and expiring sets. Confirm chain priorities and coexistence with all host firewall, Docker, VPN, namespace, routing and NAT rules. Any uncertain route or bypass is a blocker.
* Ensure every relevant proxy egress interface is the guarded bridge; prohibit host networking, extra Docker networks, published ports, direct host access, privileged containers, `CAP_NET_ADMIN`, Docker socket access and untrusted changes to networking/firewall. Prevent client containers from bypassing the proxy through other interfaces; the guard permits **any** TCP/443 traffic to allowed IPs from the bridge, not only traffic from the proxy. There is no trusted source-address enforcement in this prototype; enforce and test client network isolation independently. Basic authentication alone is not source control, and its credentials traverse the client-to-proxy network in plaintext; use only a suitably isolated trusted transport and verify that assumption. Limit access and protect client credentials.
* On boot, Docker daemon restart, proxy restart, management process crash and host firewall reload, verify that the guard exists **before any container can send**, under the lifecycle assumptions above. Docker restart policies and live restore must not restart or preserve these containers ahead of the guard. An nftables table does not survive reboot by itself; preventing external removal while containers run remains an external prerequisite.
* Create the lease directory on the host, writable only by root; mount the **directory**, not an individual file, read-only at `/run/openai-lease` in the container (atomic replacement changes the file inode). Host and container must share the Linux monotonic clock. Neither proxy nor clients may write this directory. Provision `/run/secrets/openai-proxy-auth` as a read-only secret readable by the proxy user, containing exactly nonempty printable ASCII `username:password`, with one colon and no newline. Missing or invalid credentials prevent startup; protect the secret and rotate it by a controlled restart. Run proxy as the unprivileged image user with capabilities dropped and no privileges. The Dockerfile requires a `PYTHON_IMAGE` build argument; select and independently verify an approved immutable digest. The Dockerfile cannot enforce that the supplied argument is actually a digest. Restrict access to the listening port.
* Establish a controlled startup/rollback procedure that checks guard installation and actual rules before allowing the proxy to run. If table creation fails, including an already existing table, bootstrap fails and the proxy must not start; Docker and unrelated workloads must remain unaffected. Recovery of an existing table requires stopping and verifying all relevant containers first; never delete it while they can run. A supervisor restart retains the guard and replaces its container; a guard restart requires controlled teardown and reinstall.
* Integration-test from the actual containers: allowed IPv4 TCP/443; denied other IPv4 addresses/ports, IPv6, host and other networks; direct client bypass; DNS rotation, invalid results and failure; stopped/killed manager and expiry; interrupted nft update; proxy/host/Docker restarts and reboot; preexisting tables; firewall reload; concurrent Docker lifecycle; and packet behavior of previously established flows after expiry. Verify TLS failures for wrong certificates and names. Confirm a local bridge client can reach the proxy without violating the intended isolation. Stop on any unexpected success or unverified path.

## Rollback

First stop and verify stopped **all** containers that could use the bridge, and prevent their automatic restart. Only then may an authorized operator remove `table inet openai_egress_guard`, delete the lease and restore the previous configuration. Do not remove the guard as a way to restore connectivity while the containers are running. No changes to host networking are performed by this prototype except when the manager is explicitly run.

## Local tests

Run `python -m unittest -v test_controls.py` in this directory. These mocked unit tests check management and lease decisions; they do not prove nft syntax, kernel enforcement, Docker isolation, startup ordering or production safety.
