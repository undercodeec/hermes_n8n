# Prueba local candidata: HAProxy TCP/SNI

No es configuración de producción. Docker DNS resuelve `api.synthetic.test` a un upstream TLS ficticio mediante un alias en una red interna exclusiva. No se publican puertos ni se usan credenciales, OpenAI, recursos previos ni volúmenes persistentes. El upstream genera dentro del contenedor un certificado y clave efímeros; el cliente de prueba desactiva la validación del certificado únicamente para esta prueba sintética. No demuestra autenticación TLS ni es ejemplo para clientes reales.

Con Docker Desktop y contexto `desktop-linux`, ejecutar `./run.ps1` desde cualquier directorio. El script muestra la configuración renderizada antes de crear recursos, usa un proyecto aleatorio y elimina únicamente sus propios contenedores y red. Requiere imágenes `node:22.15.0-bookworm` y `haproxy:3.0.11-alpine`, descargadas si faltan. Prueba SNI permitido, distinto, ausente y upstream detenido. Los negativos requieren resolución DNS y conexión TCP al proxy, y lo sondean antes y después; no aceptan fallos de DNS o conexión como éxito. Tras detener también el proxy, una regresión comprueba que los tres negativos fallan por indisponibilidad. Esto no prueba disponibilidad continua ni el motivo interno exacto del cierre TCP.

SNI es una declaración del cliente, no una identidad de destino autenticada. DNS contaminado puede dirigir el proxy a otro servidor que reciba el tráfico con el SNI permitido; en producción el cliente debe validar certificado y nombre, además de existir controles adecuados de DNS y destino. La allowlist tampoco impide que otro proceso omita el proxy, ni inspecciona HTTP, ni representa un firewall completo. ECH y cambios de protocolos requieren análisis separado. No habilitar esta configuración en producción sin diseño y validación independientes.
