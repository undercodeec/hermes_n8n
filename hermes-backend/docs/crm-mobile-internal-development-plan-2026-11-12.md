## 1. Evidencia, límites y decisión de producto

- **Observado en este checkout, no necesariamente integrado:** backend NestJS 11/TypeScript, Prisma 5/PostgreSQL, Redis/BullMQ; integraciones Meta WhatsApp, Nous, n8n y Google Calendar según código y actas con fecha. Controladores y DTO citados abajo se inspeccionaron estáticamente aquí. No se ejecutó ninguna API autenticada ni se verificó un servidor desplegado.
- **Piloto distinto:** `docs/inbox-order-validation-2026-11-10.md` registra diferencias materiales frente a la base piloto, incluyendo filtros de origen, proyecciones públicas CRM y migraciones adicionales. Su HEAD de comparación histórico no equivale a HEAD actual ni al despliegue. Antes de implementar, comparar contratos en el **HEAD exacto del piloto que se vaya a usar** con pruebas autenticadas y de seguridad. No trasladar controladores o servicios completos desde este checkout al piloto.
- **Frontend no auditado:** la existencia de panel Web/admin Next.js aparece en documentos históricos, no constituye inspección de código frontend, componentes reutilizables ni resultado de pruebas en móvil. El handoff `crm-mobile-feasibility-20261112` está **pendiente de recepción/verificación** y sirve para coordinar contratos y flujos, no para reabrir la elección nativa aprobada. Un PR integrado, imagen publicada y versión efectivamente desplegada son estados diferentes: ninguno se deduce aquí.
- **Objetivo:** operadores internos de una sola empresa atienden el Inbox de WhatsApp con trazabilidad, dentro de guardas comerciales y de privacidad existentes. No hay modelo multiempresa/`tenantId`/aislamiento por tenant probado. Usuarios internos con roles `ADMIN` y `SALES_AGENT`; los permisos de acción y recurso deben diseñarse/validarse, no inferirse de un rol global.

### MVP / exclusiones

**MVP propuesto:** ingreso seguro de personal, cierre y revocación de sesiones por dispositivo, lista paginada y detalle de conversaciones, historial, respuesta manual _solo online_ y dentro de la ventana Meta, toma/asignación/resolución controlada de handoff, visualización protegida de medios, consulta y actualización limitada de tareas/leads, reuniones **solo lectura** si el piloto expone contrato seguro; actualización por eventos con reconciliación. Telemetría sin contenido privado y accesibilidad móvil básica.

**Fuera del MVP:** alta de clientes externos, multiempresa, campañas/ads, pagos, administración de catálogo/tarifas, automatización de IA o activación F3/F4, programación/edición de eventos Google desde móvil, envío de media saliente, envío offline o cola optimista de mensajes, acceso directo desde el dispositivo a PostgreSQL/Redis/n8n/Meta/Nous, uso de datos reales para QA, publicación en tiendas o despliegue productivo en este encargo. Push es opcional posterior a autorización y revisión de privacidad; no incluir texto, nombres, números, archivos o previews en el payload de push **ni en el SSE propuesto como señal**.

## 2. Arquitectura API-first y decisión de cliente

```text
Operador -> app React Native + Expo (Android/iOS)
                 |-- TLS -> BFF opcional -> API NestJS /api/* -> Prisma -> PostgreSQL
                 |-- TLS -----------------> API NestJS /api/* -> Prisma -> PostgreSQL
                 `-- TLS -> SSE autenticado de API /api/conversations/events
                              ^  (BFF opcional solo como proxy autorizado)
                              `-- Redis Pub/Sub interno (señales minimizadas/autorizadas)
Webhook Meta -> API/persistencia/ledger -> workers BullMQ/Redis internos -> Meta/Nous/n8n
                                         `-> lectura/refetch CRM (no envío desde SSE)
Reuniones GET -> lectura CRM -> datos de Google persistidos (estado a verificar en piloto), no OAuth en el móvil
```

Las dos rutas API son alternativas: directa o mediante BFF; PostgreSQL y Redis solo son accesibles desde servicios backend autorizados, nunca desde la app ni directamente desde el BFF. JWT, sesión por dispositivo, RBAC por recurso, proyecciones públicas, auditoría y límites se aplican en el servidor. El cliente consume únicamente contratos versionados/saneados. BFF si hace falta para cookies HttpOnly/CSRF, streaming autenticado y normalización; nunca puente sin controles, ni acceso directo a servicios internos. Separar las acciones de lectura de las mutaciones; el servidor decide permisos, ventana de 24 h, opt-out, estado de conversación, handoff y ledger, independientemente de lo mostrado por la UI. Conservar observabilidad por request/operation ID sin payload ni PII. Un solo negocio no exime de autorización horizontal por conversación, lead, tarea o medio.

**Decisión aprobada para planificación:** React Native + Expo + TypeScript, aplicación nativa Android/iOS; PWA no es el producto principal ni una alternativa en competencia para G0. El CRM web sigue independiente. No se supone portabilidad de componentes Next. Evaluar Expo Router para navegación, SecureStore para credenciales y EAS para build/submit; fijar versiones compatibles, límites y alternativa antes de implementación. SecureStore protege secretos apropiados en Keychain/Keystore: **no** guardar allí historial, mensajes, medios ni borradores. No asumir que el runtime JS o SSE sobreviven en background: SSE solo en foreground activo, sin garantía de entrega; al regresar reconciliar por API autorizada. Push posterior, sujeto a revisión, sin PII.

**Repositorios y CI/CD propuestos:** repositorio móvil separado `hermes-mobile` (nombre por confirmar), con propiedad, permisos, ciclo de versiones y pipeline propios; repositorios CRM web y backend independientes. Contrato API versionado y fixtures sintéticos compartidos por publicación controlada, sin importar internals ni conectar directamente a DB/Meta/Nous/n8n. Estructura tentativa:

```text
hermes-mobile/
  app/                 # rutas Expo Router si se aprueba
  src/{api,auth,features,components,security,telemetry}/
  assets/  tests/{unit,contract,e2e}/
  app.config.ts  eas.json  package.json  tsconfig.json
  .github/workflows/  # u otro CI aprobado
```

CI futuro: lockfile reproducible, lint/typecheck/unitarias y contrato mock; E2E y builds Android/iOS con entornos aislados, secretos y firma en gestor autorizado, perfiles dev/preview/release y permisos mínimos. Generar AAB firmado para Play y IPA firmado para TestFlight, registrar commit, versión, build number, perfil, huella y procedencia; distribución manual aprobada o EAS Submit previa evaluación. Proteger credenciales de firma, recuperación y revocación; evitar datos reales en CI. iOS requiere cuenta/certificados/perfiles y entorno de build compatible o servicio autorizado. OTA, si se propone, exige política de compatibilidad runtime, firma, rollback y revisión de tiendas; no reemplaza actualización binaria ni controles de seguridad.

**G0:** ADR nativa con responsables de producto, móvil, backend y seguridad; matriz de dispositivos/redes, UX, identidad, costos, soporte y distribución; prototipo desechable login + inbox + reconexión + media con contratos sintéticos en ambas plataformas. Se exige diseño viable de identidad y sesiones, con riesgos y dependencias documentados, no implementación real de identidad en G0. Handoff web, BFF y presupuesto son dependencias por resolver, no motivo para volver a elegir PWA.

## 4. Seguridad, privacidad y consistencia: especificación de trabajo

1. **Sesiones revocables por dispositivo (nueva capacidad, no declarada implementada):** registro servidor de sesión con identificador aleatorio opaco y hash de token de refresco rotatorio, expiración absoluta/inactividad, vínculo al usuario/dispositivo lógico (sin huella invasiva), último uso y revocación. Access tokens cortos con `jti`/`sid`, validación en servidor de sesión activa y usuario activo; rotación atómica/replay detection, límites de dispositivos y endpoint para listar/revocar propio/ADMIN según política aprobada. Tras revocación bloquear API, SSE y refresh; probar carreras, red intermitente y desactivación. Almacenamiento cliente: Keychain/Keystore en nativo o cookies HttpOnly Secure SameSite con CSRF en Web/BFF; nunca JWT en URL, localStorage persistente, logs ni analítica. MFA/SSO y protocolo de recuperación sujetos a decisión de seguridad. Cualquier tabla/migración necesaria requiere revisión específica previa, no se crea aquí.
2. **RBAC + alcance por recurso:** matriz ADMIN/SALES_AGENT para leer/contestar conversación, ver medios, tomar/asignar/resolver handoff, editar lead/tarea, ver reunión. Servidor autoriza actor y objeto (pertenencia/asignación, relación mensaje-conversación, estado), deniega por defecto; respuesta 403/404 coherente sin enumeración. El `RolesGuard` actual y el JWT activo no bastan. Auditar mutaciones con actor, IDs y resultados sin cuerpos sensibles. Restringir campos vía proyección explícita; test de regresión con columnas privadas sintéticas (incluido `password`) en **todas** las rutas.
3. **Privacidad:** minimización en red/cliente, redacción de notificaciones/capturas/analytics, no guardar medios ni historial en caché de SO/service worker/backups; bloquear previsualizaciones de pantalla si se acuerda política, limpiar al logout/revocación, limitar retención y acceso de soporte. En modo sin conexión, solo pantalla de estado y estado UI efímero: **ningún** contenido de cliente ni borradores persistidos; push opt-in después de evaluación legal/seguridad, solo ID opaco/indicador, no nombre/texto/teléfono en APNs/FCM. Decidir TTL, notificación por rol, BYOD/MDM, consentimiento y borrado remoto antes de activarlo.
4. **SSE y reconexión (bloqueante):** en este checkout `conversation-events.service.ts` (tipo `CustomerMessageEvent` y `emitLocally`) emite `contactName` y `content` a todos los suscriptores; `conversations.controller.ts` protege `events()` solo con JWT + roles ADMIN/SALES_AGENT, sin scope por conversación. Autenticación de stream **no equivale a autorización de cada destinatario**. Antes de habilitar móvil, definir payload mínimo de señal sin nombre, contenido, teléfono, texto ni previews (IDs solo si el destinatario está autorizado a conocerlos); filtrar en servidor por actor y conversación en cada evento, incluidos cambios de asignación/revocación, **o** diseñar canal por usuario con autorización efectiva y limpieza de suscripciones. Evitar que Pub/Sub/BFF/cliente retransmitan el payload amplio actual; no usar SSE actual como señal segura. Probar con dos agentes y recursos ajenos que no se entrega ni ID/PII ni evento revelador, también tras cambio de permisos, logout/revocación y reconexión. Una vez cerrado ese gate, SSE sobre sesión autenticada (BFF/cookie o cliente con cabecera segura, según plataforma) con heartbeat, backoff+jitter y límite de conexiones. Redis Pub/Sub y `Subject` no tienen replay garantizado ni eventos para todas las mutaciones: al iniciar/reconectar/volver a foreground y ante pérdida de secuencia, refetch paginado de Inbox y detalle/historial del chat abierto **autorizado**, deduplicar por ID, comparar timestamps/estado; polling de rescate medido. Nunca usar `Last-Event-ID` como garantía sin outbox/cursor durable implementado. Paginación offset no tiene snapshot entre requests: refrescar desde página 1 y deduplicar IDs si entran mensajes.
5. **Envío solo online:** botón deshabilitado si red/sesión/estado no confirmados; confirmación de ventana/opt-out/propietario en backend justo antes de enviar. Doble tap y timeout no deben emitir dos WhatsApp: diseñar clave de operación generada por cliente y deduplicación/ledger servidor con lectura de estado _antes_ de habilitar reintento; si se desconoce resultado, mostrar `pendiente de verificar`, consultar estado y **no reenviar**. Respetar STOP, handoff, respuestas automáticas y restricciones Meta existentes. No prometer exactamente una entrega con la ruta actual sin prueba de crash ambiguo.

### Matriz de almacenamiento y ciclo de vida por plataforma (diseño a verificar)

La política es evitar persistencia sensible, no garantizar que el SO o una biblioteca nunca creen copias. Inventariar y probar cada versión de biblioteca de red, imágenes, multimedia, navegación, logs y crash reporting; desactivar cachés y persistencia sensibles cuando sea posible, y bloquear la función si no se demuestra control suficiente. SecureStore solo para secretos de sesión apropiados, nunca historial o medios; validar comportamiento de Keychain/Keystore y exclusión de backups según SO, configuración y biblioteca.

| --- | --- | --- |

| Backups | Revisar Auto Backup y reglas de exclusión de archivos/preferencias y secretos; comprobar restauración sintética. | Previsualizaciones y capturas | Evaluar protección de pantalla y vista de tareas recientes, notificaciones y previews; probar según versión del SO y política BYOD/MDM. | Evaluar ocultación del snapshot del selector de apps y previews/notificaciones; probar ciclo de vida y versiones del SO. Los controles no garantizan borrado físico seguro, eliminación de capturas externas, backups previos ni limpieza inmediata en un dispositivo offline o comprometido. Documentar excepciones y límites, decidir MDM/retención con seguridad y verificar con dispositivos físicos, instrumentación y datos sintéticos antes de G4; una fuga o biblioteca sin control aceptable bloquea el gate.

### Capacidad y presupuesto propuesto (no SLO productivo)

El informe local de Inbox del 10/11 midió **10.068 conversaciones / 200.198 mensajes**, 10 lecturas **seriales** límite 50 alternando páginas 1 y 100, p50 **1.185 ms**, p95 **1.262 ms** (nearest-rank), RSS final Node 163 MiB que incluye Jest. Presupuesto local sugerido allí: p95 ≤ 2.000 ms para un lector serial, por debajo del timeout de transacción Prisma de 5 s; no prueba concurrencia ni red real. Ranking local requiere **O(N) memoria de candidatos y O(N log N) ordenación**, y la lectura relacional puede crecer también con mensajes históricos. Polling de 15 s equivale a cuatro peticiones/minuto por pestaña: no extrapolar cantidad de agentes desde ese dato.

Para G4 **proponer, no prometer**: definir fixture y hardware/índices de piloto exactos, mezcla 1/10/25 agentes concurrentes y llegada de mensajes, p50/p95/p99 servidor y extremo a extremo, CPU/RSS, consultas/planes, conexiones ocupadas, espera y timeouts, latencia SSE-refetch y tasa de errores/duplicados; objetivo inicial a negociar p95 GET Inbox ≤ 2 s con 10 agentes simulados en 10k/200k, cero truncamiento y cero dobles envíos en pruebas de fallos. Si falla, presupuestar ranking/paginación SQL parametrizada o resumen indexado revisado, sin cambiar filtros/proyecciones/snapshot por request; cualquier índice o tabla exige revisión de esquema/migración. Repetir mediciones antes de aumentar agentes, datos o frecuencia.

**Protocolo móvil G4:** acordar antes de probar modelos físicos Android/iPhone, versiones mínimas y actuales de SO, gama de memoria y redes Wi-Fi/celular degradadas; registrar modelo/SO, versión firmada, fixture, duración, condiciones y repetición. Medir arranque, tiempo de Inbox y media, p50/p95 de interacción, memoria pico/tras uso prolongado, consumo de batería por hora y tasa de fallos, con umbrales y baseline aprobados por producto/QA (no inventados como SLO). Probar bloqueo, background prolongado, suspensión o terminación por el SO, cambio de red, modo avión, pérdida de sesión y retorno: cerrar o suspender SSE en background, no exigir entrega entonces y comprobar refetch autorizado, deduplicación y estado correcto al volver. Probar revocación mientras la app duerme, pérdida de dispositivo y ausencia de datos persistidos. Evidencias sintéticas de resultados y fallos, no capturas de clientes reales.
