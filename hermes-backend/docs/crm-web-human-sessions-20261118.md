Hermes CRM web: session handoff / rollout gate (2026-11-18)

## Contract introduced in this branch

`POST /api/auth/crm-proof` still consumes the existing UnderCodeEC HS256 one-time proof (`iss=undercodeec-admin`, `aud=hermes-crm`, configured operator, `jti` stored in `consumed_crm_proofs`). It now returns `user`, a 5-minute `accessToken` (`typ=web`, `sid`, distinct derived signing key), a rotating opaque `refreshToken` and `expiresAt` (24h from the last accepted explicit activity). Web sessions are stored in `web_sessions` (migration required before the new binary). An OTP exchange creates a new independent web session; unlike mobile, it does not end other browsers.

UnderCode's proposed `POST /api/crm/auth/session-proof` can mint a fresh one-use proof from a still-valid admin session. On `POST /api/auth/crm-proof` pass `{proof, existingRefreshToken}` to **reuse** an existing valid Hermes web session atomically: consume the new proof, rotate the refresh with CAS, preserve its ID and idle deadline, do not create another record. Reusing a revoked/expired session or replayed refresh is rejected (401), not silently recreated. Without `existingRefreshToken`, an authentic new proof creates a distinct session as with a new browser/login. The existing UnderCode proof payload has no stable admin session identifier; preventing duplicate records **across clients without a retained refresh** requires a separately agreed signed stable admin-session identifier. Do not send the raw admin token as this identifier. A fresh proof without an existing refresh represents a new login and can create a new session (including after Hermes web logout), so UnderCode must explicitly decide when that is permitted.

- `POST /api/auth/web/refresh` body `{ "refreshToken": "<id>.<secret>" }`: CAS rotates once; returns the same shape as proof exchange. It **never** changes `expiresAt`. A consumed refresh cannot revoke the winner. The client must serialize requests and persist the replacement token before any further refresh/logout.
- `GET /api/auth/web/session` (web bearer): `active`, `expiresAt`, `idleRemainingMs`; no renewal.
- `POST /api/auth/web/activity` (web bearer): only explicit foreground human gestures; sets idle deadline to now + 24h if the session is still valid. Caller must not invoke it from timers, refresh, GET, SSE, reconnect, focus/visibility/wake or automatic retries. A bearer holder can simulate activity: this endpoint cannot cryptographically prove humanity.
- `POST /api/auth/web/logout` (web bearer), `POST /api/auth/web/logout-refresh` (current refresh body; useful after short access expiration), `POST /api/auth/web/revoke-all` (web bearer, configured operator only). Revocation is per session or all Hermes web sessions, never UnderCode admin sessions. Password `/api/auth/login` and `/api/auth/register` still issue their existing legacy JWT shape/lifetime; these do **not** acquire the new session policy. Mobile access/refresh remain isolated.
- All Hermes routes using the regular JWT guard verify the web session in PostgreSQL before accepting web JWTs, including direct API calls. SSE handshake uses this guard and its outgoing events check revocation/idle in DB, closing on access JWT expiry (at most 5 minutes) or the next heartbeat/event after revocation; no heartbeat updates activity. Clients must refresh and reconnect; a connection cannot outlive a 5-minute web access JWT.

## Required cross-system handoff (UnderCodeEC integration worktree is read-only here)

The UnderCodeEC worktree `crm-otp-revoke-inbox-integration` issues web `proof` **and** `adminToken` from `/api/crm/auth/verify-code`; Hermes verifies only the OTP proof. The admin token belongs to UnderCodeEC and is **not** a Hermes credential; never accept it directly without a server-to-server validation protocol. UnderCode's CRM currently saves Hermes `accessToken` only in `sessionStorage`, checks `/auth/profile`, and clears all sessions on any Hermes 401; `/conversations/events` also reconnects with this token. Its new `useAdminHumanActivity` calls only UnderCode `/api/admin/activity`, **not** Hermes. Therefore enabling this branch without updating its client ends usable CRM sessions after ~5 minutes even when the UnderCode admin session is healthy.

Handoff update: UnderCode's agent plans `/api/crm/auth/session-proof` guarded by `adminAuth` (new `jti`, `aud=hermes-crm`, 120s). Hermes supports reexchange above. UnderCode must not auto-reexchange after an explicit Hermes revoke/logout when that revocation is intended as a security lockout; a live admin token can otherwise mint a brand-new proof. To enforce cross-system revocation immediately, agree a trusted binding/revocation contract before rollout.

Request UnderCode handoff to: retain the Hermes refresh token in session-only protected storage (avoid logging or URL params), serialize refresh rotation globally per tab; refresh proactively before the 5-minute access expiry (a generic 401 does not distinguish expired JWT from revocation, so do **not** blindly refresh/retry on every 401); retry a request once only after a successful expected rotation and reconnect SSE with new access; attach Hermes `/auth/web/activity` to the **same real trusted foreground pointer/keyboard interactions** as `/api/admin/activity`, never to idle/background traffic; validate **both** sessions on resume before unlocking CRM; on logout call both UnderCode admin logout and Hermes web logout/logout-refresh; decide policy for admin-token expiration/reset while Hermes stays valid (a Hermes web bearer alone can still call Hermes directly until its own idle deadline or revocation). Coordinate an authenticated server-to-server revoke/link mechanism if immediate cross-system admin-token revocation is mandatory; this branch does not infer admin revocation from client storage.

## Migration, safety and limits

Deploy the additive `web_sessions` migration first, then a **synchronized** backend/client rollout (or gate the OTP exchange until the updated client is present). Never deploy the new backend alone to the current web client. An old backend on rollback does not know the distinct-key web JWTs, so new sessions require re-login; additive table can remain. Mixed-version backend replicas cannot verify these web tokens: avoid mixed serving or drain older replicas. Existing 7-day legacy tokens, including any **already issued** web proof JWTs indistinguishable from password JWTs, remain valid until natural expiry unless a separate reviewed legacy-token revocation/migration plan is approved. Similarly `/api/auth/login` password clients remain 7-day JWT clients and can bypass the new idle policy; do not claim universal 24h enforcement. UnderCode admin tokens are currently in-process; its restart independently invalidates them while Hermes web sessions can persist. Decide whether to revoke Hermes sessions through a trusted cross-system hook on UnderCode logout/reset or fail closed in a coordinated frontend only; frontend-only logout is not immediate server-side cross-system revocation. No production services or data were touched here.
