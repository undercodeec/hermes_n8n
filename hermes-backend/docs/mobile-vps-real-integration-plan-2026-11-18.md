# Integración móvil en VPS real — plan de ventana, 18/11/2026

## Decisión y alcance

El propietario decidió usar el **VPS real** como entorno de integración y no continuar preparando pruebas locales para esta fase. Indicó que no habrá usuarios conectados durante una ventana de 24 horas y que existe un backup externo de los datos; aceptó el riesgo de pérdida de datos y recuperación prolongada para avanzar. La disponibilidad de esa ventana, la fecha exacta de inicio y fin y el estado de las sesiones deben confirmarse inmediatamente antes de operar. La ausencia de usuarios no demuestra que no haya colas, webhooks o escrituras automáticas: inspeccionarlos y definir su tratamiento antes de la ventana. El backup y su restauración **no han sido verificados por esta revisión**; no afirmar RPO/RTO ni recuperabilidad demostrada. `BACKUP-01` queda abierto hasta ampliar capacidad y ejecutar restauración aislada.

El alcance propuesto es autenticación con el buzón ya autorizado, un operador y un teléfono, sesiones web/móvil y lectura del Inbox real. El propietario confirmó que el operador de gerencia puede consultar todas las conversaciones de WhatsApp. No activar `MOBILE_REPLY_ENABLED`, no habilitar compositor ni enviar mensajes WhatsApp a Meta durante la prueba. No almacenar ni registrar OTP, proofs, JWT, secretos, `.env`, datos de clientes ni capturas del Inbox. Limitar la revisión de datos a lo estrictamente necesario y obtener confirmación del propietario si aparece una decisión adicional de privacidad o acceso a dispositivo.

**Este documento es un plan, no evidencia de despliegue ni instrucción de ejecutar una ventana automáticamente.** Antes de cada acción productiva se informarán destino, versión o digest, secuencia, impacto y recuperación; cualquier requisito obligatorio de un procedimiento aplicable que exija restauración real se revisará y no se dará por cumplido mediante la aceptación genérica del riesgo. Si se requiere excepción, presentar explícitamente el alcance y obtener decisión por operación.

## Secuencia propuesta

1. **Antes de la ventana:** confirmar horario real, ausencia de usuarios, responsable y canales de parada; inspeccionar runtime, ramas, imágenes, espacio, procesos, estados de BD, proxy/TLS, flags y restricciones de despliegue. Confirmar los medios y ubicación del backup externo con el propietario, sin solicitar ni publicar credenciales; anotar que su restauración sigue sin prueba. Guardar de manera segura referencias de las versiones anteriores, no valores sensibles. Validar que el operador autorizado, el buzón y los dos servicios tienen la configuración compatible, reportando solo coincidencias o estados, nunca valores.
2. **Preparación de release:** revisar/integrar los PR y sus dependencias según la estrategia aprobada, fijar commits, producir una imagen Hermes por digest inmutable y una versión concreta de API UnderCode, y registrar integridad y procedencia. Definir las rutas HTTPS y controles de acceso; no usar `localhost`, Mailpit ni datos sintéticos como evidencia de conexión real. Mantener el envío móvil apagado.
3. **Inicio de ventana:** pausar temporalmente el canje de nuevos logins cuando sea necesario; registrar hora de último OTP/proof sin guardar su contenido. Comprobar que las rutas actuales y la UI web están en el estado esperado y que hay un camino de recuperación. Detenerse si aparece actividad de usuarios no prevista, no se identifica el destino de una BD, hay problemas de capacidad, las versiones no son reversibles o surge una incompatibilidad no evaluada.
4. **UnderCode API:** aplicar la migración OTP aditiva únicamente a la base identificada, verificando previamente esquema y estado parcial. Publicar la versión específica de la API, reiniciar solo su proceso según el procedimiento de PM2 y comprobar salud, correo autorizado y login web. No sustituir la publicación web Next.js por la actualización del proceso API.
5. **Hermes:** aplicar migraciones Prisma identificadas solo a PostgreSQL identificado, registrando resultados sin datos privados; desplegar el digest aprobado recreando únicamente `hermes-app` conforme a su runbook, sin recrear bases ni volúmenes. Verificar salud, logs sanitizados, ausencia de reinicios y compatibilidad del login web. Si fallan las comprobaciones, detener la prueba y aplicar el plan coordinado, no proseguir con el móvil.
6. **Prueba real autorizada:** con HTTPS y certificado válidos, solicitar OTP al buzón autorizado sin imprimirlo, comprobar ingreso web y móvil, un solo teléfono, Inbox e historial en solo lectura, sesión simultánea, revocación desde web y logout. Verificar rechazo de tokens móviles en rutas legacy de escritura y que el envío móvil está deshabilitado, sin realizar intentos que creen mensajes. La prueba de inactividad de 30 minutos exige medir el tiempo real; no confundir actividad o refresh con interacción. No afirmar prueba iOS si no hay dispositivo.
7. **Cierre:** informar versiones/digests efectivamente activos, migraciones aplicadas, verificaciones, incidencias y hora; no publicar datos de clientes ni credenciales. Mantener observación durante la ventana acordada y documentar riesgos, pendientes y resultado de limpieza del dispositivo.

## Parada y reversión coordinada

- Priorizar deshabilitar nuevas funciones y detener canjes si falla autenticación o aparecen efectos inesperados. Conservar tablas, volúmenes y evidencia; no improvisar SQL inverso, `DROP`, borrados ni reprocesos de mensajes.
- Si se vuelve a la API OTP anterior, pausar nuevos logins y dejar caducar o reemitir OTP pendientes: el código antiguo no utiliza el nuevo almacén. Si se vuelve a Hermes anterior que no consulta el ledger durable de proofs, detener canjes y esperar **al menos 210 s desde el último proof firmado** (180 s de validez más 30 s de tolerancia), salvo un procedimiento coordinado alternativo revisado.
- Recuperar por separado el digest anterior de `hermes-app` y la versión anterior de API PM2, siguiendo sus runbooks; verificar salud y login web. No afirmar que el rollback de código revierte migraciones o recupera datos. Los tokens/sesiones móviles podrían requerir nuevo ingreso.
- Ante pérdida o corrupción de datos, activar el procedimiento de recuperación con el backup externo comunicado por el propietario; **su existencia y restaurabilidad no están verificadas aquí**. Informar límites y tiempo real de recuperación, sin prometer RPO/RTO.

## Evidencia previa y límites

Existen pruebas locales previas de OTP/Mailpit, Android con datos sintéticos, carga y restauración de esquema sintético, pero el propietario decidió que la siguiente fase sea en VPS real. Esas pruebas no acreditan SMTP real, HTTPS, compatibilidad productiva ni restauración del backup externo. Este plan tampoco acredita una prueba real ni autoriza envío móvil.
