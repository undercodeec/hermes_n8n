# G4: respuesta MANUAL móvil (contrato y rollback)

**Estado:** rama de desarrollo, sin despliegue. POST deshabilitado por defecto; requiere `MOBILE_REPLY_ENABLED=true` **después** de revisar la migración SQL, ensayar la concurrencia con cambios de autorización y aprobar explícitamente el envío. No reutiliza el POST web `/api/conversations/:id/reply`. La lectura Inbox/SSE es un módulo separado; el cliente móvil de staging solo monta lectura y NO llama a esta ruta.

## Contrato

- `POST /api/mobile/conversations/:conversationId/replies`, bearer JWT móvil vigente, header `Idempotency-Key: <uuid>` y JSON `{ "operationId": "<mismo uuid>", "content": "texto" }`. Ambos IDs obligatorios e iguales (comparación sin distinción de mayúsculas). Una operación UUID es global: mismo UUID, mismo actor, conversación y cuerpo exacto representa una única intención; contenido o conversación distinto devuelve **409**. Contenido: texto no vacío tras trim, máximo 4096 caracteres. Nunca cambiar el UUID tras un timeout del cliente para intentar repetir la misma intención.
- `GET /api/mobile/conversations/:conversationId/replies/:operationId`: estado del intento propio. Nunca intenta despachar. No devuelve contenido ni destinatario ni credenciales. Respuesta: `{ operationId, status, messageId, wamid, createdAt, dispatchStartedAt, confirmedAt, rejectedAt, rejectionCode, ambiguousAt, retryable }`. `retryable=true` solo para PREPARED; para reanudar use **el mismo UUID y contenido** mientras el handoff, sesión, ventana y opt-out permitan el despacho. GET solo para el autor original autenticado con sesión móvil activa.
- POST devuelve **202** con el mismo cuerpo de estado: `PREPARED` (solo si quedó antes de claim y el cliente consulta GET), `DISPATCHING` (intento reservado; resultado incierto), `CONFIRMED` (wamid y mensaje registrados juntos), `REJECTED` (Meta devolvió rechazo HTTP definitivo, sin entrega aceptada), `AMBIGUOUS` (timeout/ausencia de wamid o fallo de persistencia después de Meta). Nunca reintentar automáticamente con otro UUID; REJECTED requiere corrección y una nueva intención explícita del operador. No equiparar DISPATCHING/AMBIGUOUS con error seguro ni con envío confirmado; prohibido reintentar con un UUID diferente sin conciliación manual de Meta. Un GET puede observar `DISPATCHING` transitoriamente incluso si el primer POST sigue en vuelo.
- Errores: **400** UUID/contenido o ventana de 24h vencida (`WHATSAPP_TEMPLATE_REQUIRED`); **401** token/sesión/operador no autorizado; **403** opt-out o token web; **404** operación no propia/conversación inexistente; **409** `OPERATION_CONTENT_MISMATCH`, `OPERATION_ID_MISMATCH`, `HUMAN_HANDOFF_REQUIRED`, conversación no WhatsApp; **503** `MOBILE_REPLY_DISABLED`. No se genera plantilla ni se envía automáticamente fuera de ventana.

## Invariante de despacho

La primera transacción crea PREPARED bajo lock de UUID con actor/hash SHA-256 del JSON `[conversationId,actorId,content]`. Una **segunda transacción** revalida operador ADMIN configurado (`CRM_OPERATOR_EMAIL`), sesión no revocada, conversación HANDED_OFF con handoff IN_PROGRESS del actor, opt-out, canal WhatsApp y último inbound <24h. Bloquea filas relevantes y confirma `PREPARED → DISPATCHING` antes de invocar Meta. Un único claim de PREPARED gana; DISPATCHING y AMBIGUOUS nunca son elegibles para reenvío incluso tras crash o timeout. Se invoca `MetaService.sendTextMessage` solo después del commit, nunca dentro de una transacción Prisma. Si Meta devuelve wamid, una transacción única inserta Message HUMAN con `metadata.source=crm_mobile`, actualiza conversación y audit log y confirma ledger + wamid/messageId. Un rechazo HTTP definitivo se guarda como REJECTED con código seguro; no se reintenta automáticamente. Si el commit de confirmación falla, se marca AMBIGUOUS en best effort; un fallo de BD puede dejar DISPATCHING, igualmente no reintentable. El proveedor no ofrece deduplicación externa: esto prioriza **a lo sumo un intento** frente a entrega garantizada. Un cambio de consentimiento/handoff tras el commit del claim y antes del request a Meta no puede cancelarse atómicamente con un tercero: **este riesgo P1 impide habilitar el flag sin aprobación operativa y prueba de carrera**. Los logs de este endpoint no incluyen texto, waId, token de autenticación ni credenciales de Meta.

## Decisión de gate (17/11/2026): mantener bloqueado

El operador eligió **no aceptar todavía** `DISPATCHING` como punto de no retorno para revocaciones u opt-out posteriores. Mantener `MOBILE_REPLY_ENABLED` sin configurar y el cliente en solo lectura: ni el código actual ni añadir una revalidación justo antes de Meta garantizan cancelación, porque la mutación puede confirmar inmediatamente después o durante el request externo. No presentar `revoke-all`, opt-out ni cierre de handoff como garantía de no envío para una operación que ya obtuvo el claim. Esta decisión no autoriza desplegar ni enviar mensajes.

Próximo diseño y prueba, **solo en aislamiento con Meta simulado**: barreras controladas inmediatamente después del commit del claim; para cada mutación (sesión revocada, contacto en opt-out y handoff cerrado), confirmar el cambio antes de liberar el intento y observar estado del ledger, número de llamadas mock y conciliación. Cubrir también timeout, crash y fallo de persistencia tras una aceptación mock; no convertir `DISPATCHING`/`AMBIGUOUS` a PREPARED ni reintentar con UUID nuevo automáticamente. Comparar alternativas de cancelación y gestión de operaciones en vuelo con el dueño del producto; documentar sus límites de garantía antes de una nueva decisión explícita. Las pruebas actuales cubren mutaciones **anteriores** al claim, no estos intercalados posteriores.

## Validación reproducible (solo simulación)

`npm ci && npx prisma generate && npm run build && npm test -- --runInBand mobile-reply.service.spec.ts`. Integración opt-in en Windows con Docker y dependencias instaladas: `./scripts/run-mobile-postgres-tests.ps1 -Suite reply`. El runner crea PostgreSQL desechable en loopback con nombre aleatorio `hermes_mobile_reply_test_<32 hex>`, usuario de prueba, aplica migraciones y borra el contenedor en `finally`. La suite exige ese nombre y usuario y rechaza URL compartidas o con parámetros; no usa el `DATABASE_URL` del entorno del usuario. Meta siempre es un mock. No insertar números reales ni conectarse a Meta en pruebas.

## Rollback / recuperación

Antes de un eventual despliegue, revisar migración aditiva `20261117200000_mobile_reply_ledger` y backup/restauración de base en entorno aislado. Para desactivar envío, quitar `MOBILE_REPLY_ENABLED` (valor por defecto deshabilitado). Revertir código/imagen a versión anterior **sin borrar** tabla ni enum: conservar UUID, estados y wamid para auditoría y conciliación de operaciones en vuelo; nunca reinterpretar DISPATCHING como PREPARED ni lanzar retries en un worker. Conciliar manualmente wamid con Meta y el historial de mensajes antes de cualquier actuación humana. El downgrade destructivo de la migración necesita autorización separada, backup y resolución de todas las operaciones; no se entrega SQL de DROP. Nada aquí acredita un despliegue productivo.
