# Plan de cierre: arquitectura de API web y móvil (G4)

**Alcance del propietario:** un operador existente, web y un teléfono a la vez, 30 minutos de inactividad real sin vencimiento absoluto adicional; conservar diseño aprobado. No crear cuentas, roles ni gestión de permisos. La demo móvil no representa datos productivos y las pruebas no envían WhatsApp.

**Estado inicial:** autenticación G2 (PR #29) y cliente opt-in G3 (PR #28) siguen en borrador; el proveedor OTP (PR #6) es una dependencia separada. El Inbox posterior al login de G3 aún muestra datos ficticios. No llamar a esto solución de CRM móvil hasta pasar los gates.

## Cinco entregables y criterios verificables

1. **API móvil de datos:** namespace `/api/mobile/inbox` separado de los controladores web; actor móvil activo y correo de operador autorizado en cada petición. Proyecciones allowlist sin metadata interna, página y orden deterministas, detalle e historial autorizados por conversación. El cliente debe identificar explícitamente demo frente a datos reales, refrescar al abrir/volver a primer plano y reconciliar por ID. Gate: tests HTTP/BD con recursos accesibles/no accesibles, paginación concurrente y ausencia de datos privados. Si no hay política de visibilidad por conversación validada, no exponer endpoint.
2. **Eventos y respuestas seguras:** SSE móvil no reutiliza eventos web con nombres/textos; emitir solo señales de invalidación tras comprobar sesión y acceso al recurso, heartbeat y cierre al revocar. No prometer replay en Redis Pub/Sub: reconectar significa releer. La respuesta móvil requiere autorización, idempotency key única por operación y ledger durable con estados de resultado conocido/desconocido; mismo ID/cuerpo es una sola intención, ID repetido con cuerpo diferente → 409. Un timeout tras invocar Meta queda **ambiguo** y jamás se reenvía automáticamente. Gate: tests de doble toque, carrera, timeout/crash, revocación durante stream, sin llamadas externas reales. Mantener respuesta móvil deshabilitada hasta pasar gate y aprobar la migración SQL.
3. **Renovación y replay:** refresh rotatorio CAS de un solo uso; respuesta perdida bloquea pantalla, no ofrece una ventana de gracia ni devuelve el token nuevo a un portador del viejo. Reutilización devuelve 401 sin revocar automáticamente al ganador (evita logout forzado con token antiguo). Nueva OTP o revocación desde web resuelven un posible compromiso. Gate: pruebas de concurrencia, pérdida de respuesta, robo que gana la carrera y revocación desde web, escritura fallida y no extensión de inactividad por refresh.
4. **Logout offline:** endpoint de revocación por refresh **vigente** aun con JWT de acceso expirado, sin rotar para cerrar. Cliente bloquea y borra almacenamiento seguro de inmediato, distingue «revocación remota confirmada» de «no confirmada» y muestra vía de revocación web. Gate: logout online/offline, fallo SecureStore, respuesta tardía y reinicio de app sin desbloqueo; jamás afirmar cierre remoto si falló.
5. **Contratos y pruebas entre procesos:** OpenAPI y documento de rutas web/móvil (audiencias, JSON, 400/401/403/409/429, inactividad, reintentos y reconciliación). Contract tests HTTP con UnderCode OTP + Hermes, PostgreSQL/MariaDB desechables, correo capturado por Mailpit sin relay, operador sintético solo en tests, cliente Android sobre HTTPS de integración y revocación web. Gate: pruebas reproducibles con SHA, bases identificadas y migraciones explícitas; cero SMTP externo y cero mensajes WhatsApp; iOS pendiente de dispositivo, no marcado como aprobado.

## Orden y dependencias

- **A (sin envíos):** cerrar auth G2/G3, reglas de offline y documentación; lectura móvil aislada y eventos minimizados; revisar seguridad y ejecutar suites locales.
- **B (todavía sin envíos reales):** ledger de respuesta móvil con migración aditiva en PostgreSQL, adaptador Meta simulado, pruebas de idempotencia y reconciliación; activar envío solo con revisión operativa específica.
- **C (integración aislada):** contratos HTTP de ambos servicios, SMTP capturador, Android y web con identidad sintética. Si faltan pruebas o recursos, mantener borradores; los builds/exportaciones no son evidencia E2E.
- **D (producción, después de autorización de ventana):** backups de ambas bases restaurados en aislamiento, digest y HEAD efectivos, migraciones por componente, pruebas de regresión web, observación y rollback coordinado. Véase `mobile-g2-vps-integration-preflight-2026-11-17.md` para estado observado y espera ≥210 s tras último proof antes de volver al backend anterior.

**Regla de salida:** no marcar los cinco puntos como terminados por una implementación parcial, una prueba unitaria sin integración o un PR publicado. No desplegar para validar una hipótesis. Registrar el resultado y el bloqueo de cada gate de manera separada.

## Avance verificable en rama de desarrollo (sin cierre de gates productivos)

- Punto 1: API de lectura y cliente de staging opt-in implementados en ramas compatibles; la app predeterminada continúa en demo. El ranking SQL y el cursor v2 se ensayaron contra PostgreSQL local migrado, **4 pruebas integradas** y 6 unitarias de Inbox. Un EXPLAIN local de primera página sobre 10k/200k sintéticos tomó 44,982 ms SQL (una muestra, sin clientes concurrentes). Falta benchmark de concurrencia, paginación profunda y recorrido HTTP+teléfono contra ambos servicios.
- Punto 2: SSE mínimo implementado en backend sin datos privados, pero el cliente aún no lo consume (usa reconciliación manual y al foreground); ledger y POST móvil idempotente implementados **deshabilitados por defecto**; 4 pruebas PostgreSQL con Meta mock. Pendiente: resolver/aceptar la carrera revocación/opt-out/handoff frente al envío después del claim, probar estrés y reconciliación, aprobar SQL y flag; cero mensajes enviados. No declarar mensajería móvil terminada.
- Punto 3: backend CAS sin gracia y cliente fail-closed ante resultado ambiguo implementados; unitarias y HTTP sintético ejecutados. No existe un modo transparente de recuperar un refresh que se rotó pero cuya respuesta se perdió: requiere OTP nuevo como decisión explícita.
- Punto 4: endpoint logout con refresh vigente y UX offline/desconocido; acción revocar teléfono en CRM web con confirmación. Falta E2E en web/teléfono frente a procesos reales de integración.
- Punto 5: documentos y pruebas de contrato por componente, 120 suites/2092 unitarias backend G4, 6 HTTP auth, 39 pruebas cliente, exportación Android con opt-in. **No** equivalen a SMTP capturado de extremo a extremo, integración de dos backends con un teléfono ni iOS. Los tres PR originales siguen en borrador hasta pasar los gates. No se aplicó SQL ni se actualizó runtime del VPS.

**Prueba HTTP cruzada posterior (17/11/2026, opt-in):** `test/mobile-cross-service.integration-spec.ts` pasó **1 prueba** levantando Express OTP de UnderCodeEC y Nest Hermes en loopback, con PostgreSQL y MariaDB migrados expresamente y SMTP capturado en Mailpit local; los tres contenedores se eliminaron. Solo se usaron identidad/destinatario sintéticos y no se llamó a Meta. Se observaron OTP de audiencia web/móvil, rechazo de proof cruzada/replay, sustitución de teléfono, lectura Inbox y revocación HTTP desde token web sin perder sesión web. El ensayo usa la **acción API** de revocar y no la interfaz web ni una app/teléfono; tampoco verifica SMTP del buzón autorizado ni producción.

**Gate P1 de respuesta:** auditoría de `mobile-reply.service.ts` confirmó que revocación de sesión, opt-out o cambio de handoff pueden confirmarse entre el commit de `DISPATCHING` y el envío a Meta. Un recheck reduce el intervalo pero no garantiza cancelación atómica de un proveedor externo. Antes de habilitar `MOBILE_REPLY_ENABLED`, decidir formalmente si el commit es punto de no retorno y cómo informar/conciliar operaciones en vuelo; ensayar intercalados después del claim para las tres mutaciones. El flag permanece apagado; no hay pruebas con WhatsApp real.
