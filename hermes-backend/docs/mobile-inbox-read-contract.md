# Mobile Inbox G4 — contrato de lectura (sin envío)

Solo `GET /api/mobile/inbox`, `GET /api/mobile/inbox/events`, `GET /api/mobile/inbox/:id` y `GET /api/mobile/inbox/:id/messages` usan JWT móvil Bearer de 5 min. No hay endpoint de escritura, media, cambios de estado ni reply. El operador debe ser ADMIN activo, tener sesión móvil vigente/no revocada y coincidir con `CRM_OPERATOR_EMAIL` (mismo valor predeterminado usado por autenticación móvil). Se revalida el actor en BD en cada petición. Las rutas CRM legacy siguen prohibidas para JWT móvil. El alcance de recursos es `channel = whatsapp`, tanto en conversación como en mensajes mediante relación; fuera de alcance responde 404.

Lista: `limit` 1..50 (20 por defecto), `status` opcional, `cursor` opcional; orden `updatedAt DESC, id DESC`. Mensajes: `limit` 1..100 (50 por defecto), orden `createdAt DESC, id DESC`; cursor opaco de la última fila (`at`, `id`). Devuelve `{ data, nextCursor, reconciliation: "restart" }`; `nextCursor = null` al final. Los cursores no son snapshot permanente: tras una señal SSE, reconexión, foreground, cambio de filtros o desplazamientos concurrentes, **descartar el cursor y volver a página 1**, deduplicar por ID. Las páginas individuales usan transacciones RepeatableRead; no se promete consistencia entre páginas. Cursors inválidos 400, recursos ausentes 404. Aplicar `ValidationPipe` global (whitelist, forbidNonWhitelisted). El resultado solo incluye IDs, estado, fecha, contacto `{id,name,phone}`, último mensaje en lista, y mensajes `{id,conversationId,direction,sender,type,content,createdAt}`. `content` solo en tipo TEXT. No devuelve rawPayload, metadata, email, media, atribución ni diagnósticos. No se exponen archivos adjuntos.

SSE es canal de **señales sin datos privados** (`connected`, `heartbeat` y `reconcile` cada 15 s). `reconcile` significa "refrescar página 1", no "llegó un mensaje". No hay IDs de evento ni replay; se ignora Last-Event-ID; no se usa el canal CRM legacy de payloads privados. Cada ciclo verifica sesión y actor en BD y vencimiento del access JWT; en revocación, vencimiento o fallo de BD termina el stream. Al cerrar el cliente cancela el timer. La revocación es acotada por el intervalo de 15 s, NO instantánea. SSE no renueva sesión o JWT. Reabrir stream con token nuevo tras refresh del cliente. No depender de SSE para completitud: reconciliar también en foreground/reconexión; el polling es invalidación periódica y puede perder cambios transitorios entre lecturas.

## Reply futuro — diseño, NO habilitado

Antes de habilitar `POST /api/mobile/inbox/:id/reply` diseñar/revisar esquema y ledger transaccional con clave de idempotencia por operador+conversación, digest canónico del payload, unicidad, bloqueo por recurso, ventana WhatsApp de 24h revalidada en servidor, autorización y sesión en cada transición, despacho durable con recuperación tras crash, deduplicación de provider y conciliación de respuestas ambiguas. El mismo `Idempotency-Key` y payload devuelve siempre la misma operación/estado; misma clave y payload diferente devuelve 409; un retry jamás debe provocar segundo envío. Estados propuestos: `PREPARED`, `DISPATCHING`, `CONFIRMED`, `REJECTED`, `AMBIGUOUS` (estado incierto no autoriza reenvío automático). Respuesta futura: `{operationId, state, messageId?, providerId?, retryable: false}`; HTTP 202 para PREPARED/DISPATCHING/AMBIGUOUS, 200 CONFIRMED, rechazo explícito para REJECTED. No reutilizar el `reply` legacy: no tiene este ledger. Requiere revisión específica de esquema/migración y de seguridad antes de implementar.
